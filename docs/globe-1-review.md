- Clean four-file split for the experiment surface (`meta`/`params`/`index`/`experiment`).
- Strong typing: `SpringValue`, `EasingValue`, `SnakePhase`, `SnakeRoute` are real interfaces, not `any`.
- Thoughtful comments where they matter (e.g. why `MARKER_RADIUS == GLOBE_RADIUS`, why the label needs a wrapper, why sub-step the spring).

### What's off
- **`experiment.ts` is 1782 lines doing six unrelated things**: math helpers, `CountryMarker` class, `SnakeController` class, `SnakeIcon` class, the DialKit DOM-injection editor, and the render bootstrap. Each section is fine; the file is too big.

- **Default values disagree** between `params.ts` and `standalone.ts:FALLBACK`. The standalone export ships with different defaults than what the gallery preview shows the user. See §7.

## 3. Webflow copy-paste readiness — **the section that matters most for the deploy**

The embed contract is solid, but there are five concrete issues that will bite on a real Webflow site.

### 3.1 The IIFE supports exactly one instance per page — **bug**
`standalone.ts:206` uses `document.querySelector('[data-webgl-experiment="globe-1"]')` (singular). If a designer drops the embed twice (e.g. a mobile-only and a desktop-only block), only the first initializes. The second wrapper just shows an empty canvas.
**Fix:** loop over `querySelectorAll`, run the IIFE body per wrapper, scope all event listeners to that wrapper.

### 3.2 Window-scoped pointer listeners create cross-instance interference — **bug, related to 3.1**
`pointermove`, `pointerup`, `pointercancel` are bound to `window` (lines 347, 356-357). With multiple instances they all respond to the same pointer events, so dragging one globe drags all of them.
**Fix:** scope them to the canvas (or the wrapper) per instance. Or keep `window` but use `pointerId` matching with `setPointerCapture` to only respond to the captured pointer.

### 3.3 Zero-sized parents silently break the camera — **bug**
`standalone.ts:362-365`:
```js
const rect = canvas.getBoundingClientRect();
renderer.setSize(rect.width, rect.height, false);
camera.aspect = rect.width / Math.max(1, rect.height);
```
If the parent renders at `0×0` first (common in Webflow flex sections, CMS bindings, hidden tabs), `camera.aspect = 0` produces NaNs in the projection matrix and the canvas paints nothing. `ResizeObserver` will eventually call `resize()` again with real dimensions, but if `resize()` ever runs at zero, nothing recovers automatically (the NaN is in the projection matrix).
**Fix:** guard with `if (rect.width < 1 || rect.height < 1) return;` at the top of `resize()`, *and* don't render until the first non-zero resize has happened. Add `if (renderer.domElement.width === 0) return;` at the top of the render loop.

### 3.4 No aspect-ratio / min-height fallback in the embed — **medium**
`webflow-export.ts:32-34` produces `width:100%;height:100%;`. That requires the *parent* (the Webflow section/div the user pastes into) to have an explicit height. Many designers paste it into a section with `height:auto`, so the wrapper collapses to 0.
**Fix:** offer a "responsive square" sizing mode that uses `aspect-ratio: 1 / 1` (or `4 / 3` etc.). Or fall back to a `min-height: 480px`. A defensive default would be:
```css
aspect-ratio: 1 / 1; min-height: 320px;
```
Document this in the embed doc.

### 3.5 Labels can spill outside the wrapper — **medium / cosmetic**
The CSS2DRenderer's `domElement` is `position: absolute; width:100%; height:100%`, but the labels themselves are rendered outside the canvas if their projected position is near the edge (the labels have `transform: translate(-50%, -50%) translate(Xpx, Ypx)` from CSS2DRenderer plus our own `translateY(offsetY)`). Webflow sections usually don't clip overflow.
**Fix:** add `overflow: hidden;` to the wrapper style in `webflow-export.ts:32`. Sounds trivial; it isn't — the snake icon and the labels for countries near the limb both need to *not* be clipped during animation. So actually `overflow: hidden` is correct only if labels are confined to "front of globe" (which they are by the visibility test). Verify visually before committing.

### 3.6 Other things that look fine — **no action needed**
- Font stack (`ui-monospace, "SF Mono", Menlo, Consolas, monospace`) is system-only — no Webflow font-loading dependency.
- Pixel ratio is capped at 2 (`Math.min(window.devicePixelRatio || 1, 2)`) — won't melt M3 retina displays.
- `data-flow-tempo` attribute is on the wrapper — useful for debugging but not load-bearing.
- The IIFE silently no-ops when wrapper or canvas is missing (good for staging where the embed isn't placed yet).

## 4. Responsiveness audit (separate from Webflow specifics)

### What's right
- `ResizeObserver` on `canvas` (line 370) — correct primitive; fires on layout change without polling.
- `LineMaterial.resolution` is updated in `resize()` (line 368). Required for `Line2` to render the correct width.
- DPR clamp at 2 (line 361). Reasonable.
- `labelRenderer.setSize(rect.width, rect.height)` (line 367). Correct.

### What's wrong / missing
- **Initial value of `LineMaterial.resolution` uses `window.innerWidth`** (line 327). The very first frame, before `ResizeObserver` has fired, will paint the snake at the wrong width. In practice the initial `resize()` call on line 372 runs before the first `requestAnimationFrame`, so this is benign — but it's wrong on inspection.
- **No min-size guard.** See §3.3.
- **No `prefers-reduced-motion` handling.** Auto-spin runs on machines that have requested reduced motion. Easy fix: read the media query and zero out `autoSpinSpeed` when matched.
- **No `IntersectionObserver` to pause when off-screen.** The render loop runs `requestAnimationFrame` forever, even when the globe is scrolled out of view. On a long Webflow page that's a measurable battery / GPU cost on mobile. Throttle: pause the RAF when the wrapper is not intersecting the viewport.
- **`window.innerWidth/Height` for LineMaterial is the wrong space**, and there are scattered other `window` references. None of them break, but a future "fullscreen / lightbox" feature would have to find them all.

## 6. Performance assessment

### 6.1 Current load (defaults: 8 countries, 21×19 grid, trail length 31)
Easily 60fps on any modern desktop. Concerns: per-frame allocations (§7.1) — fine on desktop, measurable on a 2021 mid-range Android.

### 6.2 Per-frame allocations to fix
- **`experiment.ts:701`** — `const colorArray = new Float32Array(N * 3)` every frame. ~3 KB/frame churn.
- **`experiment.ts:770` and `standalone.ts:397`** — `sampleAt` returns `new THREE.Vector3().lerpVectors(...)` per call, called N+2 times/frame.
- **`experiment.ts:386`** — flash interpolation: `new THREE.Color(...)` per marker per frame while flashing.
- **`experiment.ts:494`** — `setAccentColor` allocates `new THREE.Color(hex)` and is called every frame from line 1507.
- **`experiment.ts:1686-1687`** — unnecessary `.clone()` before `.project()` (which mutates in place).

### 6.3 Scaling to "more countries / more nodes" — **the new section**

You said you want to add more countries. Here's what breaks at what scale, in order:

| Scale | Bottleneck | Symptom |
|---|---|---|
| 8 (today) | none | 60fps everywhere |
| ~30 | starts being noticeable on mobile | Visibility-test JS loop runs 30× per frame; CSS2DRenderer projects 30 labels |
| ~100 | **CSS2DRenderer becomes the bottleneck** | DOM writes per frame become the dominant cost; jank on mid-tier Android |
| ~500+ | architecture mismatch | Per-marker `MeshBasicMaterial` + per-marker visibility test in JS = 500 JS branches/frame |

**Specific issues that get worse linearly with country count:**
- `markers: CountryMarker[]` — each marker holds its own `MeshBasicMaterial` (line 303) or `SpriteMaterial` (line 314). 500 separate materials = 500 GL state changes/frame in the worst case.
- `updateMarkerVisibility()` (line 1439) iterates all markers and does a matrix multiply per marker on the CPU.
- CSS2DRenderer (`renderer.render()` on `labelRenderer`) projects every CSS2DObject in the scene every frame and writes `style.transform`. **This is the single biggest cost at 100+ markers.** Three.js docs explicitly warn it doesn't scale beyond a few dozen.
- The snake's "L-path" via `buildSnakePath` allocates fresh `Vector3[]` per route (80 entries per leg). In `snakeContinuous` mode the path *grows unbounded* (the comment at experiment.ts:411 says "≈3KB/leg, no pruning"). At ~1 leg/sec for an hour, that's ~10 MB. Not a crisis, but a leak.
- The flash loop (line 1647-1654) runs unconditionally per marker even when no flashes are active. Could short-circuit when no marker has `flashUntil > 0`.

**The only-fix-when-you-need-it cliff:** at ~50 markers you should switch to:
1. **`THREE.InstancedMesh`** for the crosses — one draw call, one material, marker positions in a per-instance attribute. ~10× the crosses for the same render cost.
2. **Replace CSS2DRenderer with an atlas-based label system** — pre-render text into a canvas atlas, draw labels as instanced sprites with UV per instance. Loses crisp browser-text but scales to thousands. Or accept that you're capped at ~30 visible labels and hide labels for markers behind the limb (we already do this — ensure CSS2DObject.visible flips when behind the globe so the renderer skips them).
3. **Move the front/back occlusion to a vertex shader** — pass the world-up vector as a uniform, compute `dot(normal, viewDir)` per instance, alpha out instances facing away. Drops the per-marker JS loop entirely.

The good news: the rest of the pipeline (wireframe, snake, icon) doesn't change with marker count — they're already O(1) in country count. The fixes above are localized to `CountryMarker`, `updateMarkerVisibility`, and the labels.

### 6.4 Other perf drags
- `renderer.resetState()` every frame (line 1715). Only needed when interleaving raw WebGL or another renderer. Drop it.
- `setAccentColor`, `ensureStyles`, `setSize` etc. are called every frame (~lines 1507-1522, 1667-1669) regardless of value change. Cache last value, skip on equality.

#### Item 12 — Scroll-driven pitch  *(~1-2 hours)*
**File:** `src/experiments/globe-1/standalone.ts` (the visible feature lives in the embedded version) and mirrored in `experiment.ts` for gallery testing.

**The architecture is friendly to this** because rotation is already composed of three independent contributions:
```ts
// experiment.ts:1589-1593
world.rotation.set(
  basePitch + pitchOffset + autoPitch,  // pitch
  baseYaw   + yawOffset   + autoYaw,    // yaw
  0,
);
```
Add a fourth contribution: `scrollPitch`. Don't touch the existing three.

**Step 12a — Add a `scrollPitch` accumulator.**
```ts
let scrollPitch = 0;            // radians
let targetScrollPitch = 0;
```
In the render loop, slew toward target with an exponential filter so a fast scroll doesn't snap:
```ts
scrollPitch += (targetScrollPitch - scrollPitch) * (1 - Math.exp(-dt * 8));
```
Apply in `world.rotation.set(...)`:
```ts
world.rotation.set(
  basePitch + pitchOffset + autoPitch + scrollPitch,
  baseYaw + yawOffset + autoYaw,
  0,
);
```

**Step 12b — Compute `targetScrollPitch` from scroll position.**
```ts
function updateTarget() {
  const rect = wrapper.getBoundingClientRect();
  const vh = window.innerHeight;
  // 0 when wrapper top hits viewport bottom, 1 when wrapper bottom hits top
  const raw = (vh - rect.top) / (vh + rect.height);
  const t = Math.max(0, Math.min(1, raw));
  // Map [0..1] to [-rangeRad/2 .. +rangeRad/2]
  const rangeDeg = scrollPitchRangeDeg ?? 30;
  const rangeRad = THREE.MathUtils.degToRad(rangeDeg);
  targetScrollPitch = (t - 0.5) * rangeRad;
}
window.addEventListener('scroll', updateTarget, { passive: true });
window.addEventListener('resize', updateTarget);
updateTarget();
```

**Step 12c — Expose dial knobs.**
In `params.ts` add:
```ts

scrollPitchRangeDeg: [30, 0, 90, 1], // total swing (top → bottom of section)

```

## 9. Out of scope but worth noting later

- **Accessibility.** No `aria-label` on the canvas, no keyboard rotation, no labels in the DOM accessibility tree (CSS2DObject labels are real DOM but with `pointer-events:none` and outside any landmark). For a marketing-decorative widget this may be fine; ask the client.
- **SSR / hydration mismatch.** If the Webflow customer ever moves to a framework that does SSR, the IIFE-on-load pattern works but produces no SSR markup. Acceptable for this kind of experiment.
- **Touch gesture conflicts on mobile.** Vertical swipe on the canvas currently rotates the globe. With scroll-pitch (Item 12) added, vertical swipe inside the canvas should *probably* rotate, while vertical swipe *outside* the canvas should scroll the page. Pointer events with capture on the canvas already handle this — but worth verifying on a real iPhone.
